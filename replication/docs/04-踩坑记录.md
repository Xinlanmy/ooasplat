# 踩坑记录：11 个坑

> 每条都按「现象 → 根因 → 解法 → 怎么确认修好了」写。
> 前 4 个是**一定会遇到**的（环境搭建阶段），中间 4 个是**跑起来之后**才会遇到的，最后 3 个是**归档整理时**的坑。

环境：macOS 15 / Apple Silicon / 16 GB，OOOSplat v0.8.1。

---

## 阶段一：环境搭建（必踩）

### 坑 1 · `npm run setup:engines` 直接拒绝安装

**现象**

```
$ npm run setup:engines
✗ macOS engine manifest is not hash-locked, refusing to install
```

退出码非 0，什么都没装上。

**根因**

不是网络问题，不是权限问题。打开 `engines/manifest.macos.json` 会看到：

```json
"buildStatus": "pending-first-build-and-hash-lock"
```

上游的 macOS 引擎分发**从未锁定哈希**。安装脚本发现清单里没有可信哈希，为了不装来路不明的二进制，主动拒绝。**这是安全设计，不是 bug。**

Windows 和 Ubuntu 的清单是锁定的，所以在那些平台上这一步能过——这也是为什么搜到的教程大多说「直接跑就行」。

**解法**

从**官方发布包**里提取。官方 dmg 里已经完整打包了 FFmpeg 8.1.2 / FFprobe 8.1.2 / COLMAP 4.2.1 / OOOBrush `ooo-v1.0.0`，版本与应用严格一致，比自行编译更可靠。

`tools/setup.sh` 做的就是这件事，并且**校验 dmg 的 SHA-256** 补偿了清单没锁哈希的缺口：

```bash
DMG_SHA256="b4159bb8abe22484ae1293747888ae8eb43e73018407db9bb66fb071f92c1037"
```

**怎么确认修好了**

```bash
engines/macos/arm64/bin/ffmpeg  -version   # 应输出 8.1.2
engines/macos/arm64/bin/ffprobe -version
engines/macos/arm64/colmap/bin/colmap -h
engines/macos/arm64/bin/brush_app --help
```

四个都能跑出帮助信息，说明引擎层就绪。

### 坑 2 · dmg 里提取出来的二进制被 Gatekeeper 拦

**现象**

提取完 `ffmpeg -version` 报 `Killed: 9`，或者弹「无法验证开发者」。

**根因**

从磁盘映像复制出来的文件带着 `com.apple.quarantine` 扩展属性。系统在首次执行前检查它，签名链对不上（dmg 是 ad-hoc 签名的）就直接终止。

**解法**

```bash
xattr -dr com.apple.quarantine engines/macos/arm64
```

`-r` 递归，`-d` 删除。`setup.sh` 在 `ditto` 之后自动执行这一步。

**怎么确认修好了**

```bash
xattr -p com.apple.quarantine engines/macos/arm64/bin/ffmpeg
# 应报 "No such xattr"，而不是十六进制属性值
```

### 坑 3 · `npm run dev:local` 卡死在「重新下载 Brush」

**现象**

启动应用，控制台反复出现下载进度，卡在 0% 或几十 MB，网络一断就重来。等十几分钟也进不去界面。

**根因**

`dev:local` 会先调 `scripts/brush-runtime.mjs` 的 `prepareBrush()`。它把**已安装的** Brush 二进制与 manifest 里记录的 `binarySha256` 比对。

问题在于：那个哈希是 OOOBrush 归档中**原始**二进制的哈希，而实际安装的是从 dmg 出来、**经过重签名**的运行时版本。两者按设计永不相等。

于是每次启动都判定「安装被篡改」，转而去重新下载 114 MB。

**解法**

跳过 `prepareBrush`，直接调 Tauri CLI，但**复用上游自己导出的配置**，这样 `--features local-colmap` 和资源映射行为和官方 `dev:local` 完全一致：

```bash
CONFIG=$(node -e "import('./scripts/local-tauri.mjs').then(m => console.log(JSON.stringify(m.localConfiguration('darwin'))))")
node node_modules/@tauri-apps/cli/tauri.js dev --features local-colmap --config "$CONFIG"
```

`tools/run-dev.sh` 就是这个。**关键是复用 `localConfiguration()` 而不是自己拼参数**——自己拼一定会漏掉资源映射，然后 COLMAP 找不到引擎。

**怎么确认修好了**

应用窗口在 1～2 分钟内出现，且「引擎状态」页四个引擎都是绿色。

### 坑 4 · `cargo: command not found`（但明明装了 Rust）

**现象**

`setup.sh` 报缺少 cargo，可是 `~/.cargo/bin/cargo` 确实存在。

**根因**

rustup 装到 `~/.cargo/bin`，但它只在**交互式 shell 的初始化脚本**里被加进 PATH。脚本用非交互方式运行时不加载 `.zshrc`，所以 PATH 里没有。

**解法**

脚本里显式加：

```bash
export PATH="$HOME/.cargo/bin:$PATH"
```

`run-dev.sh` 和 `setup.sh` 都加了。

**怎么确认修好了**

在脚本上下文里 `command -v cargo` 有输出。

## 阶段二：跑起来之后

### 坑 5 · `--projects-root` 用相对路径报 `INVALID_PATH`

**现象**

```bash
splatstudio generate video.mov --quality balanced --projects-root ./out
# Error: INVALID_PATH
```

**根因**

CLI 把 `--projects-root` 直接传给后端的路径校验，校验要求绝对路径（防止工作目录变化导致项目写到意外位置）。相对路径不会自动 resolve。

**解法**

```bash
--projects-root "$(cd .. && pwd)/splat-projects"
```

**怎么确认修好了**

项目目录出现在你指定的位置，且 `project.json` 里 `projectsRoot` 是绝对路径。

### 坑 6 · 命令行中断 = 前面全白跑

**现象**

跑到 5535/15000 步时中断（Ctrl+C 或超时），重新执行同样的命令，**从抽帧开始重来**。

**根因**

`bin/splatstudio.rs` 只暴露了 `generate`，没有 `resume` / `continue` 之类的子命令。断点续跑的逻辑写在 GUI 里（「继续生成」按钮），CLI 没有暴露这个入口。

所以：**SfM 的结果虽然还在磁盘上，但 CLI 不会去复用，直接重建。**

**解法**

- 想中断就用 **GUI**，它的「继续生成」会从检查点接上，复用已完成的 SfM
- 用 CLI 就跑到底，别中途停
- 真要长时间跑，套一层 `caffeinate -i` 防休眠

**怎么确认修好了**

GUI 里中断后点「继续生成」，日志应从训练步数接着走，而不是重新出现「提取特征」。

### 坑 7 · 特征提取花了 57 分钟，按公式只该 8 分钟

**现象**

精细档，特征提取阶段耗时 56.9 分钟。按第 2 次（均衡档）的像素数和帧数线性外推，应该在 8 分钟左右。

**根因**

当时的机器状态：

- 空闲内存 **约 100 MB**
- swap 已用 **1.46 GB**
- **Docker 在后台运行**

不是算法慢，是在和 swap 抢磁盘。COLMAP 的特征提取是内存密集型，一旦开始换页，速度会掉一个数量级。

**反证**：后来同样的均衡档、同样的 1920 长边，提前关掉 Docker 后训练速度 **15.3 步/秒**，而之前只有 **8.3 步/秒**——参数完全没改，**快 1.84 倍**。

**解法**

跑之前：

```bash
# 看谁在吃内存
ps aux | sort -k4 -rn | head -10
# 看 swap
sysctl vm.swapusage
# 关掉 Docker Desktop（它是最大户）
```

**怎么确认修好了**

`vm.swapusage` 的 used 在训练期间不超过 200 MB，且训练日志的步/秒稳定。

### 坑 8 · 注册率 100%，画质却更差

**现象**

一段素材拿到 307/307 全注册、平均轨迹 8.77（都是四次里最好的），splat 只有 17.2 万，渲染出来形体粗、背景一堆灰麻点。

**根因**

两个原因叠加：

**① 注册率是整幅画面的指标。** 那段素材的背景是一整面亮白墙加玻璃隔断。纹理弱，但面积占画面 80% 以上、亮度高、帧间一致——COLMAP 在这些区域匹配得非常轻松。于是 307 帧全部注册。但这个 100% 里贡献最大的是背景，不是物体。

物体只占画面高度 **18%**，折算到 1920 短边约 270 px。上一段素材是 490 px——每个方向少 1.8 倍，面积少 **3.3 倍**。

**② 浅景深背景产生伪特征点。** 虚化区域在每一帧里的模糊形态都不一样，SIFT 会提出「位置像是对的、实际偏移」的特征点。重建出来的点就飘，肉眼表现为一片灰麻点。

**解法**

拍摄端改，不是参数端改：

- **让物体占画面高度的一半以上**。这是最有效、最容易被忽略的一条
- 小光圈（f/8 以上）让背景也实焦，或者让物体占满画面把背景挤出去
- 走完一圈，**距离保持不变**

**怎么确认修好了**

别再看注册率。看两个数：

```bash
# 预算利用率：splats / max_splats
# 低于 30% 说明素材喂不饱算法，加预算没用
```

以及肉眼估一下物体在画面里的高度占比。

## 阶段三：归档整理

### 坑 9 · 日志里的「预计提取 N 帧」不等于实际帧数

**现象**

统计脚本第一版把「预计提取 113 帧」当成实际抽帧数写进 CSV，结果和磁盘上的文件数对不上。

**根因**

应用有三层帧数：

1. 按档位规划的**目标**帧数（日志里「预计提取 N 帧」）
2. Bridge 判定重叠不足后**自动补的**帧数
3. 最终**落盘**的帧数 = 1 + 2

只有第 3 个才是 COLMAP 实际处理的帧数，也才是注册率的分母。

**解法**

不要解析日志文本，直接数磁盘：

```python
frames_on_disk = len(glob.glob(f"{project}/frames/*.jpg"))
bridge_added = frames_on_disk - frames_planned
```

`tools/collect_stats.py` 就是这么做的。

**怎么确认修好了**

`frames_planned + bridge_added == frames_on_disk`，且 `registered <= frames_on_disk`。

### 坑 10 · `final.ply` 推不上 GitHub

**现象**

```bash
git push
# remote: error: File final.ply is 120.16 MB; this exceeds GitHub's file size limit of 100.00 MB
```

**根因**

单个 PLY 37–120 MB，取决于 splat 数量（每个高斯 62 个 float ≈ 248 字节）。精细档轻松破百。

而且它是**结果不是代码**，本来也不该进版本库。

**解法**

两个层面：

**① 仓库层面** —— `.gitignore` 排除：

```gitignore
*.ply
*.splat
*.spz
*.sog
splat-projects/
```

**② 想分享结果** —— 用 `results/` 里的对比图（每张不到 1 MB），或者把 PLY 传到 Release / 网盘，README 里给链接。真要托管大文件，Git LFS 也行，但没必要为了一个演示模型引入 LFS 依赖。

**怎么确认修好了**

```bash
git ls-files | grep -E "\.ply$"   # 应该没输出
du -sh .git                       # 应该在几 MB 量级
```

> **注意**：如果 PLY 已经被 commit 过一次，光加 `.gitignore` 没用——它还在历史里。需要用 `git filter-repo` 或重建仓库。**所以要在第一次 commit 之前就把 `.gitignore` 写好。**

### 坑 11 · 项目目录名带随机后缀，脚本硬编码路径会失效

**现象**

```bash
cd splat-projects/20261118-211407_IMG_4066   # No such file or directory
```

**根因**

项目目录命名规则是 `{时间戳}_{素材名}_{8位哈希}`，哈希每次运行都不同。同素材重跑一次就是新目录。

**解法**

用 glob 取最新：

```bash
D=$(ls -dt splat-projects/*IMG_4066*/ | head -1)
```

`ls -dt` 按修改时间倒序，`head -1` 取最新的。注意 glob 要带斜杠后缀，否则匹配到文件时 `ls -d` 行为不同。

**怎么确认修好了**

```bash
echo "$D"   # 应该是一个真实存在的目录
```

## 如果只能记住三条

1. **坑 3 是最容易劝退的**——启动就卡住，看起来像网络问题，实际是哈希比对的设计冲突。`run-dev.sh` 就是为它写的。
2. **坑 7 的收益最大**——关掉 Docker 换来 1.84 倍速度，比换档位、换配置都划算。
3. **坑 8 最反直觉**——指标全绿但结果差，因为指标度量的是整幅画面而不是你的物体。
